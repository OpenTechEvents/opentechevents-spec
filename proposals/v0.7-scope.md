# v0.7 — scope, decided on verified evidence

Status: proposal. Written 2026-11-06, after the review of [#55](https://github.com/OpenTechEvents/opentechevents-spec/issues/55)
and [#56](https://github.com/OpenTechEvents/opentechevents-spec/issues/56) and the `ote-tools`
agent's answers to five questions. **Nothing here is implemented.** The ordering and the exclusions
are the point of the file: three of the candidates that looked urgent are not spec work at all, and
one of my own earlier conclusions was wrong.

## The correction that reshapes everything

I said most of this could ship now as prose, with only the new schema file waiting for a version
fork. **That was wrong, and it is wrong for the reason this repo just wrote down**: normative prose
lives in `spec/vN.N/README.md`, and v0.6 is frozen. So does `spec/vN.N/examples/`. Naming the
feed-member class, stating the support window, and adding member examples are all *additions to
normative material*, and an erratum corrects, it does not add.

Therefore: **almost everything below needs the fork.** Only `versions.json` lives outside `spec/`
and can ship immediately. That is the argument for forking v0.7 sooner rather than accumulating.

### Not in v0.7: generated, lives outside `spec/`

- **`versions.json` with `publishedAt` derived from the npm registry's `time` map**, gated by
  `--check`. Can ship today. Hand-typed dates are a second source of truth, which is forbidden by
  [`CLAUDE.md`](../CLAUDE.md#principio-de-proyecto-la-vía-determinista).
- **`event-member.schema.json`**. Downgraded from "the fix" to a citation convenience, on the
  `ote-tools` agent's own test: `standaloneCode` accepts a fragment key and emits a named entry
  point (`validateFeedMember`, 355387 bytes), in a browser bundle, with no ajv at runtime. If it is
  added anyway it must be **generated** from `event.schema.json`. Decide after D044, not before.

## Rejected, with the premise that fails

- **"The media type and `/.well-known/ote-feed` are undecided."** They were settled **in v0.6**:
  `spec/v0.6/README.md` — *"Settled in v0.6 … The media type is `application/ote+json`"*, and
  `/.well-known/ote-feed` is an explicit **MAY**, with the reasoning. Issue #33 is **closed**. The
  IANA registration is an external process, not a change to the document. Consequence for the
  skill: it can stop warning organizers that the value may change. Nothing to do in the spec.
- **"The recommended profile pushes `cfp` and `closesAt` onto a 20-person meetup."** It does not.
  The global recommended set is `description, organizers, attendanceMode, location, tags,
  languages, updatedAt`; `cfp` appears only as a conditional — *if* the document has a `cfp`, then
  it needs `closesAt`. Nothing recommends adding one.
  **But there is a real residue underneath it**: for a document without `partOf`, the profile
  recommends `url` and `image`, and that is exactly the warning D034 already paid for once. If
  segmenting the recommended profile is worth doing, this is the pair to argue about — not `cfp` —
  and it is cheap because the profile does not affect validity.

## Not spec work at all

The four blockers the skill actually hit were tooling, by the `ote-tools` agent's own ranking, and
one of them is live damage to the adopter verified in #56: `report.valid === false` for an
out-of-window document whose schema errors are zero, which makes the badge on Community Builders'
README red today and the web validator say *"Invalid OTE document"*. The spec's part is only to
state the rule that forbids it (D047); the fix is theirs, and it is more urgent than any of this.
